BLD Security & Data Protection

Complete picture of how we protect marketplace data, client/surveyor PII, and internal staff — plus the target state for a highly secured database and app.

Honest note: no system is “100% secure.” This blueprint defines a gold-standard control set (defense in depth) so BLD can be audited, hardened, and operated as highly secure in practice.

Defense-in-depth model

Every request and every row of data should pass multiple independent controls.

1. Edge / network
HTTPS (ALB / Nginx / CloudFront), private VPC for DB, WAF optional, no public DB ports.
2. Identity
Auth0 + app JWT sessions; OTP for email/phone; scrypt password verifiers; no anonymous write paths except deliberate public endpoints.
3. Authorization
Memberships (client / surveyor / admin) + staff permission presets + ownership checks on projects, matches, tickets, notifications.
4. Application
Zod validation, rate limits, signed S3 URLs, MIME/size caps, log redaction, PII minimization in API responses.
5. Database
Private Aurora, encryption at rest (KMS), TLS in transit, Secrets Manager credentials, least-privilege DB users, backups + PITR, audit logging.
6. Data lifecycle
Terms/NDA gates, retention/deletion policy, suspended users enforced, cascade-safe deletes, activity logs for staff actions.

Protecting users — marketplace & internal staff

Clients

See and mutate only their projects. Match peer PII minimized (username/city vs full name).

Surveyors

Only their offers/profile. Portfolio/media under their key namespace. Matchable only when profile complete.

Internal staff

Separate admin hat + admin_profiles. Fine-grained permissions. Super admin locked from normal staff UI delete/suspend.

Dual-role users

One identity, multiple memberships. Workspace activeRole is UI routing only — API still checks membership + ownership.

Implementation roadmap

Do these in order — each phase raises the security floor without boiling the ocean.

Phase 1 — Close critical app holes (1–2 weeks)

Enforce suspended users · media delete ownership · production CORS fail-closed · disable AUTH_DEV_MODE in prod · Helmet + security headers · require DB SSL in connection strings · document AWS KMS + SG checklist.

Code status (repo): suspended-user guard + login/Google checks · media DELETE ownership · CORS fail-closed · devAuthEnabled on JWT path · Helmet on Nest · production DB SSL boot check · this ops checklist below.
Still ops: verify Aurora KMS encryption + security groups in AWS.

Phase 2 — Session & edge hardening (2–4 weeks)

httpOnly cookie sessions + refresh rotation · OAuth state binding · Redis-backed rate limits · optional AWS WAF · pgaudit / CloudWatch DB audit · least-privilege DB roles + credential rotation drill.

Phase 3 — Data protection maturity

Field-level encryption for sensitive PII · retention & erasure API (GDPR-style) · soft-delete where needed · backup restore game-day · security review / pen-test.

Operator checklist — “DB highly secured”

Print this for staging and production. All boxes should be true before calling the environment highly secured.

  • ☐ Aurora in private subnets; SG allows only Proxy / ECS
  • ☐ Storage encryption enabled (KMS CMK)
  • ☐ App DATABASE_URL uses SSL (sslmode=require or stronger)
  • ☐ Credentials only in Secrets Manager; rotated; not in git or CI logs
  • ☐ Separate migrate vs app DB users (least privilege)
  • ☐ Automated backups + PITR enabled; restore tested in last 90 days
  • ☐ Staging and production fully isolated (no shared DB)
  • ☑ Suspended / deleted users cannot authenticate (Phase 1 code)
  • ☐ Staff actions permission-gated; super admin protected
  • ☑ Media keys private; deletes ownership-checked; downloads signed (Phase 1 code)
  • ☐ Auth tokens not readable by JavaScript (httpOnly) — Phase 2
  • ☐ Audit trail for privileged DB and staff actions

Phase 1 — AWS KMS + security group verification

  • ☐ RDS / Aurora → Configuration → Encryption = enabled (KMS key noted)
  • ☐ DB subnet group = private subnets only (no public IP)
  • ☐ DB / Proxy security group inbound: TCP 5432 from ECS task SG (or Proxy SG) only
  • ☐ ECS task SG outbound to Proxy/DB only as needed; no world-open 5432
  • ☐ Secrets Manager holds DATABASE_URL with sslmode=require
  • ☐ CORS_ORIGINS / WEB_APP_URL set in the environment (API will not boot otherwise)
  • ☐ AUTH_DEV_MODE unset or false; NODE_ENV=production

Automated check (needs AWS CLI credentials): powershell -File scripts/verify-phase1-aws.ps1 -Region <region>
