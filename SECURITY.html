Defense-in-depth model

Every request and every row of data should pass multiple independent controls.

1. Edge / network
HTTPS (Nginx + Certbot on staging; ALB in production design), per-IP Nginx rate limits on auth and API routes, private VPC for DB, no public DB ports. Managed WAF (Cloudflare / AWS) is the next step.
2. Identity
Auth0 + first-party sessions in httpOnly cookies (15-minute access token, rotating refresh token with reuse detection); OTP for email/phone; scrypt password verifiers; OAuth state signed and bound to a nonce; no anonymous write paths except deliberate public endpoints.
3. Authorization
Memberships (client / surveyor / admin) + staff permission presets + ownership checks on projects, matches, tickets, notifications.
4. Application
Zod validation, Redis-shared rate limits, Helmet + CSP, CORS fail-closed, custom session header on cookie requests (CSRF), signed S3 URLs, MIME/size caps, log redaction, PII minimization in API responses.
5. Database
Private Aurora, encryption at rest (KMS), TLS in transit (enforced at API boot), Secrets Manager credentials, least-privilege DB users, backups + PITR, audit logging.
6. Data lifecycle
Terms/NDA gates, retention/deletion policy, suspended users enforced, cascade-safe deletes, activity logs for staff actions.

What is already in place

Controls currently implemented in the monorepo and deploy docs.

Live Auth by default

Global JwtAuthGuard; only @Public() skips auth.

Live Auth0 + first-party JWT

JWKS RS256 validation; HMAC app sessions; timing-safe verify.

Live Password & OTP hardening

scrypt password verifiers; OTP stored as SHA-256 hash, TTL, single-use.

Live Staff RBAC

@Roles('admin') + @RequirePermissions; super-admin protected.

Live Ownership scoping

Projects, matches, feedback, helpdesk, notifications scoped to the right party.

Live Media controls

Auth upload, MIME allowlist, size caps, user-namespaced keys, presigned GET.

Live Infra target

Private VPC, RDS Proxy → Aurora, Secrets Manager, ALB HTTPS (see deploy/aws/README.md).

Live Onboarding legal gate

Terms + NDA timestamps required before workspace unlock.

Live httpOnly cookie sessions

Web tokens are not readable by JavaScript. 15-min access cookie + rotating refresh (auth_refresh_tokens, reuse revokes the family). Cookies are only read with the X-BLD-Session: cookie header (forces CORS preflight → CSRF defense on top of SameSite). Mobile keeps tokens in SecureStore.

Live Suspended users blocked

Login, Google sign-in, refresh and every guarded request reject non-active users; suspend and password reset revoke all refresh tokens.

Live OAuth state binding

Signed, short-lived OAuth state bound to a nonce in an httpOnly cookie (web) or request body (mobile) — blocks login CSRF.

Live Headers, CSP, CORS

Helmet on the API; CSP + frame/referrer/permissions headers on web. Production CORS fails closed when CORS_ORIGINS / WEB_APP_URL are missing.

Live DB TLS enforced

API checks pg_stat_ssl at boot and refuses to start on a cleartext Aurora connection; deploy refuses non-sslmode=require URLs.

Live Shared rate limits (Redis)

API throttler backed by a private, password-protected Redis (bld-redis, no host port). Limits hold across API restarts and instances; swap REDIS_URL to ElastiCache with no code change.

Live Edge rate limit on auth

Nginx per-IP limits before the API: /api/auth/* credential routes 20/min (burst 20) → 429; other /api/* 20/s (burst 100). Config auto-rolls back if nginx -t fails.

Live Post-deploy verification

verify-staging-security.yml runs after every API deploy: Aurora encryption (via EC2 instance role, no stored AWS keys), Redis limiter, DB TLS, and a real 429 burst test.

Protecting users — marketplace & internal staff

Clients

See and mutate only their projects. Match peer PII minimized (username/city vs full name).

Surveyors

Only their offers/profile. Portfolio/media under their key namespace. Matchable only when profile complete.

Internal staff

Separate admin hat + admin_profiles. Fine-grained permissions. Super admin locked from normal staff UI delete/suspend.

Dual-role users

One identity, multiple memberships. Workspace activeRole is UI routing only — API still checks membership + ownership.

Implementation roadmap

Do these in order — each phase raises the security floor without boiling the ocean.

Phase 1 — Close critical app holes (1–2 weeks)

Enforce suspended users · media delete ownership · production CORS fail-closed · disable AUTH_DEV_MODE in prod · Helmet + security headers · require DB SSL in connection strings · document AWS KMS + SG checklist.

Code status (repo): suspended-user guard + login/Google checks · media DELETE ownership · CORS fail-closed · devAuthEnabled on JWT path · Helmet on Nest · production DB SSL boot check · this ops checklist below.
Status: Done — live on staging
Still ops: Aurora KMS confirmation (EC2 needs a read-only IAM instance role, or check the RDS console) · security groups in AWS.

Phase 2 — Session & edge hardening (2–4 weeks)

httpOnly cookie sessions + refresh rotation · OAuth state binding · Redis-backed rate limits · optional AWS WAF · pgaudit / CloudWatch DB audit · least-privilege DB roles + credential rotation drill.

Done (live): httpOnly cookie sessions + rotating refresh with reuse detection · OAuth state/nonce binding · Redis-backed rate limits (bld-redis) · Nginx edge rate limits on /api/auth/* · web CSP + security headers · post-deploy security verification.
Remaining: managed WAF (move bld.online DNS to Cloudflare, or ALB/CloudFront + AWS WAF) · ElastiCache when running more than one API host · pgaudit / CloudWatch DB audit · least-privilege DB roles + credential rotation drill.

Phase 3 — Data protection maturity

Field-level encryption for sensitive PII · retention & erasure API (GDPR-style) · soft-delete where needed · backup restore game-day · security review / pen-test.

Operator checklist — “DB highly secured”

Print this for staging and production. All boxes should be true before calling the environment highly secured.

  • ☐ Aurora in private subnets; SG allows 5432 only from the app (staging: EC2 API host · production: ECS / RDS Proxy)
  • ☐ Storage encryption enabled (KMS CMK) — not yet confirmed (no AWS read access from the box)
  • ☑ App DATABASE_URL uses SSL (sslmode=require, enforced by deploy + API boot check)
  • ☐ Credentials only in Secrets Manager; rotated; not in git or CI logs
  • ☐ Separate migrate vs app DB users (least privilege)
  • ☐ Automated backups + PITR enabled; restore tested in last 90 days
  • ☐ Staging and production fully isolated (no shared DB)
  • ☑ Suspended / deleted users cannot authenticate; refresh tokens revoked on suspend
  • ☑ Staff actions permission-gated; super admin protected
  • ☑ Media keys private; deletes ownership-checked; downloads signed
  • ☑ Auth tokens not readable by JavaScript (httpOnly cookies, rotating refresh)
  • ☑ OAuth login state signed and nonce-bound
  • ☑ Rate limits shared via Redis; Nginx per-IP limit on /api/auth/* returns 429
  • ☐ Managed WAF in front of Nginx (needs Cloudflare DNS or ALB/CloudFront)
  • ☐ Audit trail for privileged DB actions (staff actions: activity_logs ☑)

Phase 1 — AWS KMS + security group verification

  • ☐ RDS / Aurora → Configuration → Encryption = enabled (KMS key noted)
  • ☐ DB subnet group = private subnets only (no public IP)
  • ☐ Staging: Aurora security group inbound TCP 5432 only from the EC2 API instance's security group (no 0.0.0.0/0, no office/home IPs left open)
  • ☐ Staging: EC2 security group inbound only 80/443 (Nginx) + SSH restricted; API :4000 and Redis not reachable from the internet
  • ☐ Production (ECS design, not deployed yet): DB / RDS Proxy SG inbound 5432 from ECS task SG only; ECS task SG outbound to Proxy/DB only
  • ☐ Secrets Manager holds DATABASE_URL with sslmode=require (staging today: GitHub Environment secret → EC2 .env)
  • ☑ CORS_ORIGINS / WEB_APP_URL set — staging API is running, and it refuses to boot in production without them
  • ☑ NODE_ENV=production and dev login off — staging logs the production-only [db-tls] check, and AUTH_DEV_MODE is force-disabled in production

Automated checks:
• No AWS keys needed: GitHub Actions → Verify staging security (runs after every API deploy; asks AWS from the EC2 box using its instance role — nothing is stored in GitHub, and public logs show only yes/no results).
• With an AWS CLI profile: powershell -File scripts/verify-phase1-aws.ps1 -Region <region>
